00_contexto.md

Por Que Isso Importa Agora

Até aqui, cada módulo do curso viveu em um projeto pequeno e isolado: o Pokédex, a Biblioteca em SQLite, a Biblioteca em Room, o HabitTracker. Em projetos desse tamanho, dá pra sobreviver com tudo meio solto dentro de um único pacote ui — o projeto é pequeno o bastante pra você guardar a estrutura inteira na cabeça.

Isso muda a partir de agora. O Projeto Final vai unir, num único app, tudo que foi ensinado neste ano: consumo de API, persistência local, navegação com múltiplas telas. Um projeto desse tamanho sem organização em camadas vira, rapidamente, um arquivo gigante onde ninguém — nem você, nem um colega de equipe — sabe onde mexer sem quebrar outra coisa. Esta aula não ensina um conceito novo de Android: ensina a organizar o que vocês já sabem fazer, da forma como times profissionais organizam.

Por que isso importa pra sua carreira: em qualquer entrevista técnica ou revisão de código (code review) profissional, a primeira pergunta sobre um projeto Android não é "funciona?" — é "onde fica a lógica de rede?", "onde fica o acesso ao banco?". Um projeto com camadas bem definidas responde essas perguntas em segundos. Um projeto sem camadas exige ler o código inteiro pra descobrir.

01_camadas.md

As Camadas e a Regra de Dependência

Separação de responsabilidades (Separation of Concerns)

A ideia central é simples de enunciar e difícil de manter na prática: cada arquivo tem um único motivo para mudar. Se a URL base da API mudou, só um arquivo deveria precisar de edição. Se o layout de uma tela mudou, só um arquivo (de UI) deveria ser tocado. Quando essas responsabilidades se misturam — uma função @Composable que também faz a chamada de rede, por exemplo — qualquer mudança pequena arrisca quebrar outra coisa, porque as responsabilidades estão entrelaçadas.

No seu projeto, essas responsabilidades já existem — só não estão separadas em pastas. Vocês vão reorganizar o código em quatro pacotes:

PacoteResponsabilidadeExemplos
networkConversa com a internet. Define o que pode ser pedido a uma API.PokemonApi.kt, RetrofitInstance.kt
dataFormato dos dados. Classes que representam a informação, local ou remota.Pokemon.kt, entidades @Entity, DAOs @Dao
viewmodelEstado e regras da tela. Decide quando buscar dados e o que a UI deve mostrar.PokedexViewModel.kt
userinterfaceO que o usuário vê e toca. Só desenha — nunca decide regra de negócio.PokedexScreen.kt

A Regra de Dependência: a seta só anda numa direção

Separar em pastas resolve metade do problema. A outra metade é uma regra que não aparece em lugar nenhum do código, mas que todo projeto profissional segue: uma camada só pode conhecer a camada logo abaixo dela nesta ordem — nunca o contrário.

userinterface
→
viewmodel
→
network / data
A seta aponta "quem depende de quem". A UI conhece o ViewModel; o ViewModel conhece a API e os dados. O caminho inverso nunca deveria existir.

Na prática: PokedexScreen.kt (userinterface) pode importar PokedexViewModel — ele chama funções dele e lê seu estado. Mas PokedexViewModel.kt nunca deveria importar nada de androidx.compose.material3 ou conhecer um Color de tela: se o ViewModel sabe desenhar algo, ele deixou de ser "estado" para virar "interface", e a separação quebrou. Essa é a versão enxuta — sem a cerimônia de interfaces e módulos Gradle separados — da Clean Architecture, a arquitetura mais citada em vagas de Android sênior: lá o princípio tem nome (Dependency Rule) e é aplicado com muito mais rigor, mas a ideia de fundo é exatamente essa seta de mão única.

Sinal de alerta: se, ao organizar seu projeto, você perceber que o ViewModel precisa importar algo de userinterface para funcionar, isso quase sempre indica que uma decisão que deveria estar no ViewModel foi colocada na tela (ou vice-versa). É um bom momento para parar e perguntar: "de quem é essa responsabilidade?"

02_refatoracao.md

Live Coding: Reorganizando o Pokédex

Vamos pegar o projeto Pokédex — que hoje tem tudo misturado dentro de com.rclepf.pokedexnovo.ui — e separá-lo nas quatro camadas. O mesmo procedimento se aplica a qualquer projeto do curso.

Passo 1 — Criar as pastas 1/6

No Project (lateral esquerda do Android Studio, certifique-se de estar na visão Android), clique com o botão direito no pacote com.rclepf.pokedexnovo → New → Package. Crie quatro pacotes: network, data, viewmodel e userinterface (esse último talvez já exista, se você seguiu o módulo da Pokédex).

Passo 2 — Mover os arquivos de rede 2/6

Arraste PokemonApi.kt e RetrofitInstance.kt para dentro de network, diretamente na árvore de arquivos (não copie e cole o texto).

Por que arrastar, e não recriar: quando você arrasta um arquivo no Project do Android Studio, a IDE atualiza sozinha a linha package no topo do arquivo e todos os imports que apontavam pra ele, em todo o projeto. Recriar o arquivo manualmente em outro lugar perde esse ajuste automático.

Passo 3 — Mover os modelos de dados 3/6

Arraste Pokemon.kt (as data class que representam o JSON da API) para dentro de data.

Passo 4 — Mover o ViewModel 4/6

Arraste PokedexViewModel.kt para dentro de viewmodel.

Passo 5 — Confirmar a UI 5/6

PokedexScreen.kt já deveria estar em userinterface, se vocês seguiram o módulo original do Pokédex. Se não estiver, mova-o para lá agora.

Passo 6 — Rodar e confirmar 6/6

Rode o app de novo (▶ Run). Se tudo foi movido por arrastar (e não por copiar/colar texto), o projeto deve compilar e rodar exatamente como antes — a reorganização não muda nenhum comportamento, só a estrutura.

Se der erro de "Unresolved reference" após mover: normalmente é um import que não foi atualizado automaticamente. Veja a seção Erros Comuns abaixo.
03_mapa.md

Mapa de Pastas Final

É assim que o Pokédex (e, depois, o Projeto Final) deve ficar organizado:

🗂️ com.rclepf.pokedexnovo
com.rclepf.pokedexnovo/
├── network/
│   ├── PokemonApi.kt          ← interface Retrofit (@GET, @Path)
│   └── RetrofitInstance.kt    ← configuração do cliente HTTP
├── data/
│   └── Pokemon.kt             ← data class do modelo (JSON)
├── viewmodel/
│   └── PokedexViewModel.kt    ← estado da tela + chamadas suspend
├── userinterface/
│   ├── PokedexScreen.kt       ← Composables
│   └── theme/                 ← Color.kt, Theme.kt, Type.kt
└── MainActivity.kt            ← só hospeda o NavHost/Theme

Em um projeto com Room (como a Biblioteca evoluída), o pacote data cresce um pouco mais: Habito.kt (@Entity), HabitoDao.kt (@Dao) e a classe @Database moram todos ali, porque todos descrevem "o formato e o acesso aos dados" — só que agora olhando para o banco local, não para a API.

99_erros_comuns.md

Erros Comuns

e: Unresolved reference 'PokedexViewModel' (ou qualquer classe movida)

Causa: o arquivo foi movido copiando o texto para um arquivo novo, em vez de ser arrastado na árvore do Project — isso não atualiza os imports nos outros arquivos que o usam.

Solução: clique no import com erro (sublinhado vermelho) e aperte Alt+Enter (Windows/Linux) ou Option+Enter (Mac) → "Import". O Android Studio preenche o import correto automaticamente, desde que o arquivo exista no pacote certo.

As pastas "network", "data" etc. não aparecem separadas no Project — tudo parece estar junto

Causa: o Android Studio tem uma opção chamada "Compact Middle Packages" ativada por padrão, que junta visualmente pacotes com um único filho numa única linha (ex: com.rclepf.pokedexnovo aparece como uma linha só).

Solução: clique no ícone de engrenagem no topo do painel Project → desmarque "Compact Middle Packages". Cada pacote passa a aparecer em sua própria linha, com indentação — mais fácil de visualizar a estrutura em árvore.

package com.rclepf.pokedexnovo.ui não corresponde à pasta do arquivo

Causa: o arquivo foi movido pelo sistema operacional (fora do Android Studio) ou colado manualmente, então a linha package no topo do arquivo ficou desatualizada em relação à pasta onde ele está agora.

Solução: edite manualmente a primeira linha do arquivo para refletir a pasta correta (ex: package com.rclepf.pokedexnovo.viewmodel), e ajuste os imports nos arquivos que o referenciam.

O ViewModel "precisa" importar algo de Compose pra funcionar

Causa: alguma decisão visual (uma cor, um texto formatado, um ícone) foi colocada no ViewModel em vez de na tela — sintoma de que a Regra de Dependência foi quebrada.

Solução: mova a decisão visual para userinterface. O ViewModel deve expor apenas dados "crus" (ex: um Int, um Boolean, um enum de estado) — quem decide como isso vira cor, ícone ou texto na tela é sempre a camada de UI.
